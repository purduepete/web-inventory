### Read-only UI review

To inspect local UI changes with live inventory data, connect Tailscale and run:

```powershell
cd client
npm run build
npm run preview
```

Open http://127.0.0.1:4173/. This serves the local build and proxies API reads and
images to https://jimbrownhome1.tail8ad282.ts.net:8795/. It checks private API access
at startup and reports an error if Tailscale or the API is unavailable.
No separate local API, database credentials or application access key is needed.

The review server binds loopback only, rejects cross-origin requests, and blocks
every method except GET and HEAD before proxying. Editing, uploads and queued
writes cannot change the live inventory. Local offline edits can still appear in
this browser's cache; they aren't saved to production. Use the deployed site when
you intend to change real data. Production builds and authentication are unchanged.
`npm run preview` reviews the last build, so rebuild after making changes.

Hover hints use the shared `Tooltip` host and `data-tip` attributes, with the
current theme's colors. Icon buttons keep an `aria-label`. Disabled buttons keep
their native disabled behavior inside a keyboard-focusable `.tooltip-trigger`
wrapper. Hints open on hover or focus and close on Escape, scroll or click.
Use `data-tip` for future hints rather than a native `title` attribute.

On iPhone and iPad, name prompts and the Add item modal open with focus on Close so the software keyboard stays closed; desktop browsers still focus the first field, and tapping a field edits it as usual.

For an agent-owned preview, use `Manage-Preview.ps1` with the current session ID:
run Status first, then Start with working directory `client`, executable `node.exe`,
arguments `node_modules\vite\bin\vite.js`, `preview`, `--mode`, `review`, and URL
`http://127.0.0.1:4173/`. Reuse the browser page and stop the preview after review.

## Household access

Access is gated by **access keys** (not Entra login). Any active key grants full
access; give each person (or device) their own so keys can be revoked individually.
Keys are generated locally — only the SHA-256 hash is stored in `inv.AccessKey`, so
the raw key is shown exactly once. Share the printed key over a secure channel; the
recipient enters it on the app's key gate (it's kept in the browser's `localStorage`).

```powershell
cd scripts
az login                                  # SQL uses your Entra identity
./New-AccessKey.ps1 -Name "jane-iphone"   # prints the raw key once — copy it
./New-AccessKey.ps1 -List                 # id, name, state, last-used (never prints hashes)
./New-AccessKey.ps1 -Disable <id>         # revoke a key (copy the id from -List)
```

There are no scopes — every active key is full access. Revoking (`-Disable`) takes
effect within a few minutes (the API caches validation results briefly).

### Backend API access protection

The API is a **bring-your-own (linked) Azure Functions backend** with its own public
URL. Access is enforced in application code by **`KeyAuthMiddleware`** (see
`api/Middleware/KeyAuthMiddleware.cs`), which requires a valid `x-api-key` on every
HTTP-triggered function and returns **401** otherwise. Functions stay at
`AuthorizationLevel.Anonymous` — the middleware is the single choke point.

Because keys are the gate, the linked Function App's App Service Authentication
("Easy Auth") is set to **allow unauthenticated requests**
(`unauthenticatedClientAction = AllowAnonymous`) so requests reach the worker where
the middleware runs. Do **not** delete the _Azure Static Web Apps (Linked)_ identity
provider; just leave it in allow-anonymous mode. The Bicep intentionally does **not**
declare `authsettingsV2`.

**Consequence:** the direct Function URL is reachable by anyone, so the middleware is
the _sole_ protection — it is deliberately **fail-closed** (missing/invalid key → 401)
and must never be removed or bypassed. A short-lived `IMemoryCache` fronts the DB key
lookup to blunt brute-force/DoS against the shared SQL database.

**Runbook — smoke tests** (run after any auth-related change):

```powershell
# through the SWA hostname
curl -i https://<swa-host>/api/containers                     # -> 401 (no key)
curl -i -H "x-api-key: <key>" https://<swa-host>/api/containers   # -> 200
# direct Function URL
curl -i https://<func-host>/api/containers                    # -> 401 (no key)
curl -i -H "x-api-key: <key>" https://<func-host>/api/containers  # -> 200
```

> **Transition note:** during the cutover from Entra, `KeyAuthMiddleware` also accepts
> a request bearing a valid SWA `x-ms-client-principal` (the platform-injected,
> un-spoofable principal) so signed-in users aren't 401'd before the key frontend is
> live. Remove this by setting `WEBINV_ALLOW_SWA_PRINCIPAL=false` (or deleting the
> branch) once the key-based frontend is fully deployed.

## Cost guardrails

- Photos are downscaled client-side (max 1024px) before upload + AI.
- Vision calls use `gpt-5-mini` at `low` image detail.
- Function App runs on Consumption; Static Web App on Standard (linked backends require it).

## Theme preferences

The header theme selector offers System, Light and Midnight, with Midnight as the default.
System follows OS changes live. The `theme` storage key accepts `system`, `light` and `midnight`;
legacy `dark` values migrate to Midnight. The icon button switches between Light and Midnight.

Run `npm test` in `client` for theme regressions. After building, set `CHECK_DIST=1` and run it again
to verify the built pre-paint script against the CSP hash. Keep `client/index.html` LF-only.
